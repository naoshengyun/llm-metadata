## 实现与操作契约

`node scripts/sync-upstream.mjs --repo /path/to/local/repo --upstream <固定提交> --business <固定提交> --output /new/isolated/candidate --protect data/naoshengyun`

可多次指定 `--protect`；自有价格、政策、来源目录必须全部列入。参数必须为仓库内普通相对路径。源仓库不被 fetch、checkout、reset、写 ref 或 push；输出必须为源仓库之外、父目录已存在的新目录（解析符号链接后检查）。创建隔离 clone，普通 `merge --no-ff` 保留双方祖先；合并失败只留在候选 clone，并以非零退出码及 JSON `status=failed/stage/error` 呈现。合并后对受保护路径执行差异门禁，即便 Git 可自动合并也不接受其价格变化。无发布或应用能力。

合并后的所有 `.github/workflows/*.yml|yaml`（含新建/重命名文件）移动到非执行目录 `.github/upstream-workflows/`，另建隔离提交。镜像上游提交原样保留。既有发布/回写 workflow 也已从本业务分支移入该目录；自有只读检查模板放在 `.github/naoshengyun-workflow-templates/`，不启用真实定时。构建生成物不提交 dist/i18n，不覆盖上游镜像。

## 托管安全与显式事件链

单 fork 的 `main` 需保持上游原样，因此代码中的分支 if 不能约束上游未来新增的未知 workflow。**托管仓库必须在镜像首次推送前保持 Actions 全局禁用**。不能用“仅移走当前两个 workflow”宣称未来 main 安全。当前没有远程 owner/仓库及启用授权，未设置任何远程权限、定时或 secret。未来若启用 Actions，须先决定如何强制隔离镜像分支上的未知工作流；未解决前维持禁用，在受控本地执行检查。模板自身不具发布权限，但它不能替代仓库层防护。

授权后的编排契约：调度记录 enabled/lastAttempt/lastSuccess/固定上游 SHA → 镜像 main 仅快进至该 SHA（不造构建提交）→ 本地候选 merge 与门禁 → 开同步 PR 至 naoshengyun → 对 PR 固定 head 显式执行检查 → 人工批准 merge → 对合并结果固定 SHA 再检查和构建独立 CNY 产物 → 产物发布另确认 → 实例应用另确认。机器人 token 不保证触发后续事件，编排器必须显式调用检查并等待固定 SHA 的成功回执；失败、未触发、超时均不得记 lastSuccess 或继续。同步成功、报价核对时间、构建成功、价格发布、实例应用为独立状态。本地候选报告明确 `published=false/applied=false/hostedActions=not-enabled`。
